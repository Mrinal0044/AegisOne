# Behavioral Intelligence Layer & Feature Store Architecture

This document provides a technical walkthrough of AegisOne's Behavioral Intelligence Layer, detailing the processing pipeline, database feature store schema, rolling window aggregation mathematics, and downstream AI integration hooks.

---

## 1. Pipeline Architecture

AegisOne implements a decoupled, event-driven architecture to transform raw industrial telemetry logs into structured feature vectors.

```
+---------------------+
|  Simulation Engine  | (Generates Modbus, S7comm, OPC-UA traffic events)
+---------------------+
           |
           | 1. Enqueue Event ID (Non-blocking)
           v
+-------------------------+
|  asyncio.Queue (FIFO)  |
+-------------------------+
           |
           | 2. Dequeue & Process Event
           v
+-----------------------------+
| BehaviorPipelineWorker      | (Continuous background daemon)
+-----------------------------+
           |
           | 3. Normalization (EventProcessor)
           | 4. Window Cutoff Generation (WindowManager)
           v
+-----------------------------+
| Aggregator Module           | (Entity-scoped SQL query aggregates)
+-----------------------------+
           |
           | 5. Upsert incremental vectors
           v
+-----------------------------+
| PostgreSQL Feature Store    | (User, Device, Asset, Dept Features)
+-----------------------------+
```

### Decoupled Background Processing
The pipeline uses an asynchronous FIFO Queue (`asyncio.Queue`) as its messaging backbone. 
- **Simulation Engine**: Publishes new database event records by enqueuing their unique UUIDs immediately after a transaction commits. This is non-blocking and adds 0ms latency to the core simulation loop.
- **Worker Daemon (`BehaviorPipelineWorker`)**: Runs as a persistent singleton background task managed inside the FastAPI lifespan context. It yields execution to await new IDs from the queue, preventing high CPU load or API blocks.

## 2. Rolling Time Windows

To capture user and device behaviors across different temporal resolutions, the aggregator computes features across 5 sliding windows:
1. **Last 5 minutes (`5m`)**: Real-time behavioral spike tracking.
2. **Last 15 minutes (`15m`)**: Short-term tactical trend analysis.
3. **Last 1 hour (`1h`)**: Operational routine pattern baseline.
4. **Last 24 hours (`24h`)**: Daily circadian shift boundary analysis.
5. **Last 7 days (`7d`)**: Long-term operational cycle and calendar baseline.

When an event triggers feature recalculation, AegisOne computes the start boundary:
$$\text{Cutoff} = \text{Reference Time} - \text{Window Duration}$$

All calculations use the **Virtual System Clock** timestamp (`event.timestamp`) rather than the host machine clock. This ensures absolute calculation accuracy during paused simulation or accelerated time-speed multipliers (e.g. 10x-120x).

## 3. Engineered Feature Vectors

### A. User Features (`UserBehaviorFeatures`)
Maintains behavioral stats for operators and engineers:
- `avg_session_duration`: Average duration of active GUI/SCADA login sessions.
- `failed_login_count`: Count of password authentication failures.
- `failed_auth_count`: Count of authentication failures or privilege violations.
- `unique_devices_count`: Count of distinct terminal workstations operated.
- `unique_assets_count`: Count of distinct PLCs and OT devices controlled.
- `commands_per_hour`: Density of writing/sending commands.
- `weekend_activity_ratio`: Percentage of transactions occurring on Sat/Sun.
- `night_activity_ratio`: Percentage of transactions occurring between 18:00 and 06:00.
- `remote_login_count`: Count of remote logins (SSH, VNC, RDP).
- `usb_usage_count`: Count of USB mount/unmount operations.
- `download_frequency`: Number of file downloads/updates per hour.
- `config_change_count`: Count of PLC configuration writes and recipe adjustments.

### B. Device Features (`DeviceBehaviorFeatures`)
Analyzes host machine and console activities:
- `active_hours`: Sum of hours the host was processing transactions.
- `connected_users_count`: Count of unique login credentials used.
- `avg_network_traffic_bytes`: Average size of payload bytes sent per event.
- `config_change_count`: Density of configuration changes generated by this host.
- `firmware_change_count`: Counts of firmware download operations originating here.
- `maintenance_frequency`: Density of updates/inspections.
- `unexpected_downtime_count`: Unscheduled reboots or critical connection losses.

### C. Industrial Asset Features (`AssetBehaviorFeatures`)
Aggregates telemetry profiles for physical field assets (PLCs, Pumps, Turbines):
- `access_frequency`: Transactions per hour targeted at this asset.
- `unique_operators_count`: Number of distinct employees reading/writing values.
- `avg_commands_count`: Ratio of command writes to standard telemetry reads.
- `alarm_acknowledgements_count`: Count of alarm resets.
- `maintenance_events_count`: Count of inspection or hardware resets.
- `operational_hours`: Active runtime calculated from telemetry ticks.

### D. Department Features (`DepartmentBehaviorFeatures`)
Aggregates baseline statistics at the organizational department level:
- `peak_activity_rate`: Highest transaction rate per hour.
- `avg_users_online`: Average number of operators active in the department.
- `unique_assets_accessed_count`: Range of industrial infrastructure accessed.
- `avg_network_usage`: Combined department network payload density.
- `typical_working_hours_ratio`: Ratio of department actions occurring during standard shift times.

## 4. Downstream AI & ML Model Integration

The Feature Store is designed to serve as the absolute boundary between raw log streams and machine learning models.

```
[ PostgreSQL Feature Store ]
            |
            | 1. Query Feature Vectors (e.g. GET /behavior/features/users?window=1h)
            v
[ Feature Vector (Pydantic / JSON) ] -> {"avg_session_duration": 28800.0, "commands_per_hour": 3.0, ...}
            |
            | 2. PyTorch / Scikit-learn Pipeline
            +--------------------------------------------+
            |                                            |
            v                                            v
  [ Feature Normalization ]                     [ Anomaly Scoring ]
  - MinMaxScaler / StandardScaler               - Isolation Forest
  - Direct feed into tensors                    - Autoencoders (Reconstruction Loss)
```

### Direct Model Consumption
In the next phase, anomaly detection models will consume vectors directly:
- **Batch Training**: ML models query the `/features/` endpoints or directly select from `UserBehaviorFeatures` to fit baseline distributions (e.g. training an Autoencoder on "normal" behavior profiles).
- **Inference Anomaly Scoring**: As the simulation runs, the AI engine periodically queries the active window vectors (e.g. `5m` or `15m`), feeds them into the trained model tensors, and triggers a `Security Alert` if the reconstruction loss exceeds the statistical threshold.
- **No Raw Logs Needed**: The models never parse Modbus headers or timestamp strings; they consume static, float-based feature matrices, maintaining separation of concerns.
